Problem Statement The comprehension of large-scale legacy and undocumented software codebases represents a persistent and economically significant challenge in contemporary software engineering practice. Despite the demonstrated potential of Large Language Models for code-related tasks, existing approaches to automated program comprehension are fundamentally limited by their reactive, query-driven, and function-level nature. No existing automated system can 15 



########## PAGE 17 ##########


 autonomously explore an unfamiliar, undocumented codebase written in a legacy or niche language, determine what it does, ground that understanding in structural and execution evidence, and produce a trustworthy, hierarchical documentation artefact from which the system can then be safely modernized, either in place or by migration, without a human first supplying a query, a language name, or prior knowledge of the system. This research addresses the following core problem: the absence of an agentic, autonomous framework capable of performing comprehensive program understanding of legacy and undocumented codebases through self-directed exploration, multi-level structural analysis, and generative documentation synthesis. The proposed framework directly addresses this gap by deploying a coordinated multi-agent architecture in which specialized agents autonomously navigate, analyze, and document unknown software systems, producing structured comprehension artifacts that reduce the cognitive burden on human developers and accelerate software maintenance and modernization activities. 4. Research Questions This research is guided by the following research questions: RQ1. How can an agentic multi-agent framework be architecturally designed to autonomously navigate, analyze, and document unknown software codebases without human guidance? RQ2. To what extent does grounding generated documentation in static program analysis and sandboxed execution evidence improve its accuracy and completeness compared with LLM-only approaches? RQ3. How does the proposed multi-agent agentic framework perform on program comprehension quality, measured by automated metrics and human expert evaluation, compared to non-agentic baseline systems? RQ4. What are the primary failure modes and limitations of the framework when applied to legacy codebases of varying complexity, scale, and language, including legacy languages with no public specification? 5. Research Objectives The research is designed to achieve the following specific objectives: • To design and implement a multi-agent architecture comprising Codebase Navigator, Language Inference, AST Analyzer, Legacy Analyzer, Dynamic Evidence, BSG Generator, Modernization Transformer, Equivalence Validator and Documentation Generator agents for autonomous comprehension and modernization of legacy codebases. • To develop a structured agent coordination protocol that governs inter-agent communication, task decomposition, and iterative self-verification within the proposed framework. 16

 • To integrate static program analysis (AST parsing, call-graph extraction, dependency analysis) with dynamic, execution-based verification so that every extracted claim is supported by evidence rather than by a second model inference. • To construct an evaluation benchmark comprising open-source legacy software repositories with verified ground-truth documentation for systematic assessment of codebase-level comprehension quality. • To empirically evaluate the proposed framework against non-agentic baseline systems using both automated metrics and human expert assessment, and to analyze its performance, limitations, and generalizability. • To specify a formal agent communication protocol, including message schema, hand-off artefacts, confidence states and escalation rules, that makes inter-agent behaviour inspectable and reproducible. 6.  6.1 System Architecture Design The framework is organised as nine agents executing over a single shared pipeline state, grouped into three stages (Figure 2). Stage 1 — Structural mapping. The Codebase Navigator traverses the repository, builds a directory and dependency map, detects the language of each file, and marks files whose language cannot be identified. For those files, the Language Inference Agent infers a working grammar in three passes: a purely statistical pass that identifies candidate keywords and block delimiters from token frequency and co-occurrence, with no model call; a hypothesis pass in which an LLM proposes syntax rules from that statistical skeleton; and a cross-file consistency pass in which any rule that cannot be confirmed in more than one file is penalised and flagged. The AST Analyzer then parses every file, using Tree-sitter grammars where the language is known and the inferred grammar otherwise, and produces an AST map, a call graph, and a table of create/read/update/delete operations against data stores. Stage 2 — Understanding and evidence. The Legacy Analyzer reads the AST map and source and proposes candidate business rules, each with pre-conditions, post-conditions, and a source location. The Dynamic Evidence Agent takes each candidate rule and attempts to reproduce the claimed behaviour by executing the relevant code path in an isolated sandbox with synthesised inputs. The outcome is one of three labels: confirmed (execution matches the claim), contradicted (execution differs), or unresolved (no safe execution path exists, for example code that depends on a live control system). The BSG Generator fuses the static claims and the dynamic outcomes into a Behavioural Specification Graph in which each rule node carries one of six confidence states: confirmed_both, confirmed_static, confirmed_dynamic, inferred, contradicted, or gap. Stage 3 — Action and proof. The BSG is the trust boundary of the system: nothing downstream is generated from raw extraction. On the user’s choice, the Modernization Transformer either upgrades the code in place (same language, deprecated patterns fixed, inline documentation added, changes needing sign-off marked REVIEW) or migrates it to a target language (idiomatic code, every interlock rendered as an explicit guard clause, unmappable constructs marked TODO rather than dropped). The Equivalence Validator re-executes the BSG rules against the new code and reports a Behavioural Equivalence Rate. The Documentation Generator produces the final hierarchical documentation, data dictionary, and graph renderings. When the Dynamic Evidence Agent contradicts a rule, the BSG blocks generation for that node and escalates it as blocked_on_human with a stated reason, while unaffected nodes continue. 18

Nine agents in three stages exchange typed artefacts through one shared pipeline state. 6.2 Agent Structure Every agent in AURA has the same internal structure (Figure 3). It consists of five parts: (i) a role specification , the agent's goal, the inputs it is entitled to read from the shared state, and the artefact it is obliged to write back; (ii) a planner , the reasoning loop in which the LLM decides which action to take next given the current state; (iii) a set of skills , deterministic tools the planner may call (parsers, graph builders, sandbox executors, retrievers); (iv) memory , split into a short-term working context for the current task and read access to the persistent shared state; and (v) a self-check , a validation step that confirms the output artefact conforms to its schema and carries provenance before it is committed. The planner cannot write to the shared state except through the self-check. This is what makes an agent's behaviour bounded: it can decide how to reach its goal, but not what it is allowed to produce. 19

 6.4 Agents and Skills The terms agent and skill are used precisely in this synopsis, and the distinction matters for the design. An agent is an autonomous unit that owns a goal, decides for itself what to do next in pursuit of that goal, invokes tools, judges its own output, and is accountable for one artefact in the shared state. It contains a reasoning loop; given the same input it may take a different sequence of steps. In the terminology of Russell and Norvig [38], it perceives (reads state), reasons (plans), and acts (calls skills and writes state). The ReAct pattern [39] is the concrete form of this loop used here. A skill is a deterministic, reusable capability that an agent can call. It has no goal of its own, does no planning, keeps no state, and returns the same output for the same input. Tree-sitter parsing, call-graph construction, statistical token analysis, sandbox execution, vector retrieval and code diffing are all skills. A skill does not know why it is being called or what should happen afterwards. The practical test is: does this component decide anything? If it decides which files to process, in what order, whether a result is good enough, or when to stop, it is an agent. If it only computes, it is a skill. The AST Analyzer, for example, is an agent because it decides how to handle a file whose parse fails (retry with the inferred grammar, fall back to line-level heuristics, or mark the file as unparseable); the Tree-sitter parser it calls is a skill. Inference is applied only to files the Navigator cannot identify, and runs in three passes: (1) a statistical pass that finds candidate keywords and block delimiters from token frequency and co-occurrence, with no model call; (2) a hypothesis pass in which an LLM proposes syntax rules from that skeleton, and any proposed keyword that does not occur in the corpus is rejected; and (3) a cross-file pass in which a rule not confirmed in more than one file is penalised and flagged. The output is a GrammarHypothesis with a confidence value per rule. Evaluation. The two hand-built legacy-dialect corpora are written from a known grammar, so the correct answer exists. Four metrics are reported per corpus (Table 5). A benchmark of ten open-source repositories will be collected from GitHub. A repository is included only if it meets all of the following criteria: 23

 1. It is at least five years old, as a rough indicator of legacy status, and has a permissive open-source licence. 2. It is written in Python or Java, and it builds and runs. 3. It has a README and some inline documentation (to serve as reference) and an existing test suite (needed to measure equivalence). 4. The set is split into three size bands: small (under 5 KLOC), medium (5 to 20 KLOC) and large (20 to 50 KLOC), with three to four repositories per band (for example 3 small, 4 medium and 3 large). 5. It comes from a different application domain; no two repositories belong to the same project family. Ground-truth preparation. Before processing, README files, docstrings, comments and documentation folders are extracted and stored as the reference, and then removed from the copy given to the framework, so that it operates under realistic undocumented conditions. Ground-truth validation. The extracted reference is validated in two steps. First, an automatic filter drops reference statements that name identifiers not found in the code, because such statements are likely outdated. Second, the author and one practitioner independently check a random 20% sample of the remaining statements against the code and mark each as correct or outdated. Agreement is reported with Cohen's kappa, and statements marked outdated are removed. Legacy-dialect corpora. In addition to the open-source set, two small corpora will be constructed by hand in invented domain-specific languages (an industrial interlock dialect and a report-scripting dialect), with at least 15 rules each. The rule list and the grammar are written before the code, so ground truth is correct by construction, and language inference and dynamic verification can be tested where no public grammar exists. 6.7 Implementation The framework will be implemented in Python. The LangGraph library [40] will be used to coordinate the agent workflow, while the OpenAI and Anthropic API clients will provide access to LLMs. Static analysis will use Tree-sitter grammars [41] for known languages and the grammar produced by the Language Inference Agent otherwise. Sandboxed execution for the Dynamic Evidence and Equivalence Validator agents will run in isolated containers with no network access and a hard time limit per rule. A web dashboard will allow a user to upload a repository, watch the agent stream, read the generated documentation and BSG, choose between in-place modernization and migration, and review the generated code together with the equivalence report. A command-line interface will remain available for batch evaluation. The implementation will be kept modular and easy to reproduce, and all code will be made available in a public GitHub repository. 24

The Behavioural Equivalence Rate (BER) is the share of testable BSG rules that still hold on the generated code. Two independent checks are used, and neither is an LLM opinion: 1. Contract tests. Each rule carries a given/expect pair from the BSG. These are re-executed against the new code with boundary-value inputs. 2. Differential tests. The same inputs are run through the original code and the new code, and the final state and any signalled faults are compared. For Python and Java repositories, the repository's own test suite is also run before and after in-place modernization, and the retained pass rate is reported. Calling conventions and equality semantics are fixed so that results are comparable across target languages. BER is always reported together with the testable share (testable rules divided by all rules), so that a high BER on a few testable rules is not mistaken for full coverage. Equivalence here means that no counterexample was found on the generated test inputs; it is evidence, not formal proof. Unresolved rules. A rule is unresolved when no safe execution path exists, for example when it calls an external system such as a database or a control system. Such code is never executed. The rule keeps a static-only or inferred confidence state, the Transformer marks the related generated code REVIEW, and the rule is listed with its reason in a gap report. Unresolved rules are excluded from the BER denominator but are counted and reported separately. Incorrectly inferred rules. A rule contradicted by execution is set to blocked_on_human together with a counterexample. The Transformer skips it, unaffected nodes continue, and the final documentation lists it as an open item. The human decision (accept, correct or discard) is recorded. 26

 Checking the safety gate. To confirm that wrong rules are handled as described, a small fixed number of deliberately false rules (about 10 per legacy-dialect corpus, where the correct rules are known by construction) is injected into the pipeline. Two figures are reported: how many of the injected rules are labelled contradicted, and whether any generated code comes from a blocked node, which should not happen. 6.10 Expected Outcomes Based on a review of related work, it is anticipated that the multi-agent approach will produce more complete and contextually accurate documentation than non-agentic baselines, particularly for larger and more complex codebases. The framework is not expected to offer significant advantages over simpler approaches for isolated, function-level documentation tasks. These expectations will be tested through the evaluation described above, and conclusions will be drawn based on the actual results obtained. It is further expected that the gap between AURA and the baselines will be widest on the legacy-dialect corpora, where no baseline can proceed without a language hint, and that dynamic verification will turn a share of statically inferred rules into evidence-backed ones and flag contradicted rules that static extraction alone would keep. The ablation is expected to show that removing dynamic verification leaves fewer evidence-backed rules and lets injected false rules pass undetected, and that removing the BSG gate lowers BER, while the effect on text-similarity scores is expected to be small. 27
